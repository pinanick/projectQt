# 1. Паспорт и архитектура CyberLab

## 1.1. Назначение

CyberLab — учебное настольное приложение на Python и PyQt6. Оно получает события входа из двух источников: встроенного генератора искусственных данных и CSV-файла. События сохраняются в SQLite, после чего анализируются двумя алгоритмами. Найденные совпадения сохраняются как инциденты. Пользователь может просматривать их, менять статус и оставлять заметки.

**Важно:** приложение не подключается к реальным серверам, не читает системные журналы и не отправляет сетевые запросы. IP-адреса и пользователи в генераторе являются демонстрационными данными.

## 1.2. Технологии

| Технология | Роль |
|---|---|
| Python | язык приложения и реализация алгоритмов |
| PyQt6 | графический интерфейс и цикл событий |
| Qt Designer | создание XML-макетов `.ui` |
| SQLite3 | локальное хранение событий, инцидентов и настроек |
| csv | чтение и запись CSV |
| pathlib | работа с путями файлов |
| collections | `defaultdict` и `deque` для группировки и временных окон |
| datetime | разбор и сравнение временных меток |

Внешняя серверная часть и ORM в проекте не используются.

## 1.4. Разделение ответственности

- `core` не должен зависеть от графического интерфейса или SQL. Анализатор получает список словарей и возвращает список найденных кандидатов в инциденты.
- `database` отвечает за хранение. `DatabaseManager` создаёт соединение и таблицы; `Repository` предоставляет методы чтения и изменения данных.
- `services` выполняет операции с внешними файлами. Здесь нет логики отображения таблиц.
- `ui` отвечает за окна, виджеты, реакцию на действия пользователя и обновление отображения.
- `config.py` хранит общие константы, чтобы не дублировать пути и подписи по всему проекту.

Такое разделение уменьшает связанность: например, алгоритм можно проверить без запуска PyQt6, а SQL-запросы сосредоточены в одном классе.

## 1.5. Полный путь данных

1. При запуске `main.py` создаёт `QApplication`, `DatabaseManager` и `Repository`.
2. Если таблица событий пуста, генератор создаёт демонстрационные события, а Repository сохраняет их.
3. `MainWindow` создаёт страницы и передаёт им один общий объект Repository.
4. Пользователь либо генерирует дополнительные события, либо импортирует CSV.
5. При анализе главное окно загружает все события и настройки первого правила.
6. Вызываются два независимых детектора.
7. Список найденных кандидатов передаётся в `Repository.save_incidents()`.
8. SQLite сохраняет только новые инциденты, учитывая уникальность пары `(ip, first_event_id)`.
9. Страницы перечитывают данные и обновляют таблицы.
10. При выборе инцидента пользователь может изменить статус и заметку. Изменения сохраняются в SQLite.

## 1.6. Модель данных

### events

| Поле | Смысл |
|---|---|
| `id` | автоматически назначаемый первичный ключ |
| `timestamp` | дата и время события в виде текста ISO |
| `username` | имя пользователя |
| `ip` | IP-адрес источника события |
| `event_type` | `login_success`, `login_failed` или `logout` |

### incidents

| Поле | Смысл |
|---|---|
| `id` | ID инцидента |
| `ip`, `username` | источник и учётная запись |
| `first_event_id` | ID события, используемого как ключ дедупликации |
| `first_seen`, `last_seen` | границы обнаруженной последовательности |
| `event_count` | число событий в последовательности |
| `status` | `new`, `investigating` или `closed` |
| `notes` | комментарий аналитика |
| `incident_type` | тип сработавшего детектора |

### rules

В текущей реализации хранится одна запись с `id = 1`: порог ошибок и длина временного окна. Ограничение `CHECK(id = 1)` отражает модель одного настраиваемого правила.

## 1.7. Два детектора

**Детектор A — частые ошибки с одного IP.** По умолчанию ищет не менее 5 событий `login_failed` от одного IP в пределах 60 секунд. Порог и окно берутся из SQLite.

**Детектор B — успешный вход после ошибок.** Ищет успешный вход для той же пары IP и username, если до него было не менее 3 ошибок в течение 120 секунд. Эти параметры сейчас заданы константами в `config.py`, а не настройками диалога.

Оба алгоритма работают с историей событий, отсортированной по времени. Они не устанавливают факт компрометации. Они лишь находят последовательности, соответствующие учебным эвристикам.

## 1.8. Что важно не перепутать на защите

- Событие — запись журнала; инцидент — результат обнаружения подозрительной последовательности.
- Генератор создаёт данные, но не выполняет атаку и не проверяет сеть.
- Алгоритмы возвращают кандидатов; Repository сохраняет их.
- SQLite — встроенная файловая база данных, а не отдельный сервер.
- PyQt6 отвечает за интерфейс, а не за анализ событий.
- Совпадение с правилом не доказывает злонамеренность пользователя.
