[db_manager.py](../database/db_manager.py) · [repository.py](../database/repository.py)

### SQL-словарь

PRIMARY KEY — уникальный идентификатор записи; FOREIGN KEY — ссылка на другую таблицу; NOT NULL — запрет NULL, но не пустой строки; UNIQUE — запрет повторения указанного значения или комбинации; CHECK — проверяемое ограничение; DEFAULT — значение при пропуске колонки. INTEGER и TEXT описывают типы/аффинность SQLite, а не строгую проверку каждого значения во всех случаях.

### Почему параметры, а не f-строки в SQL?

Параметр ? представляет значение, передаваемое драйверу отдельно от текста запроса. SQL-код остаётся фиксированным; пользовательская строка не становится его синтаксисом. Это также корректно обрабатывает кавычки в именах и комментариях. LIMIT параметризован аналогично. Имена таблиц и колонок здесь не берутся из ввода пользователя.

### Что будет при повторном анализе?

Если кандидаты имеют те же (ip, first_event_id), UNIQUE и INSERT OR IGNORE сохраняют одну запись на ключ. Это не означает, что повторный импорт CSV не создаёт дубликаты событий: events не имеет такого ограничения. Существующий инцидент не обновляется автоматически при повторном анализе, его заметки и статус сохраняются.

### Вопросы на защите

- Repository и DatabaseManager — зачем оба? Первый предоставляет операции предметной области, второй управляет соединением и схемой.
- commit и close — одно и то же? Нет. commit фиксирует изменения, close освобождает соединение.
- Почему timestamp TEXT? В учебной схеме это простой единый формат, пригодный для сортировки при нормализованных датах.
- Почему COUNT(*) не COUNT(notes)? COUNT(*) считает все строки, COUNT(колонка) — только не-NULL значения колонки.
- Почему таблица rules имеет только одну запись? CHECK(id = 1) и первичный ключ реализуют ограничение текущего дизайна.
- Что будет при неизвестном ID в UPDATE? Запрос может изменить ноль строк; код не проверяет rowcount.
- Есть ли ORM? Нет, SQL написан непосредственно в Repository.
