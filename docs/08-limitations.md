# 8. Ограничения, известные недостатки и проверка

Документ основан на статическом анализе исходников. Запуск графического интерфейса и автоматические тесты не выполнялись в рамках подготовки этой документации.

## Архитектура и данные

| Ограничение | Фактическое поведение | Возможное развитие |
|---|---|---|
| Нет подключения к реальным журналам | Источник — генератор и CSV. | Добавить отдельный адаптер доверенного источника журналов. |
| Нет фонового мониторинга | Анализ запускается кнопкой. | Отделить выполнение анализа от интерфейса. |
| Нет ML | Только детерминированные эвристики. | Оценивать качество правил по размеченным учебным данным. |
| Нет полноценного управления случаями | Статус и одна текстовая заметка. | Хранить историю изменений и дополнительные атрибуты. |
| SQLite локальна | Один файл и одно соединение. | При необходимости многопользовательской работы пересмотреть архитектуру хранения. |

## Известные особенности алгоритмов

- Первый детектор группирует по IP, но в инцидент записывает username последнего события на момент срабатывания. Это не означает, что вся последовательность относится к одному пользователю.
- event_count первого детектора — размер окна при срабатывании, а не полный размер последовательности. last_seen также фиксируется при срабатывании.
- active сбрасывается только при размере очереди ниже порога после добавления текущей записи. Некоторые границы последовательностей могут не выделяться отдельно.
- Второй детектор использует first_event_id для ID успешной записи. Имя поля не полностью соответствует смыслу для данного типа.
- Повторный анализ не обновляет уже сохранённые инциденты. Изменение параметров не пересчитывает и не удаляет старые записи.
- Уникальность определяется парой (ip, first_event_id), а не полной последовательностью и не типом инцидента.
- Отсутствует измерение точности на размеченном наборе (precision, recall, false positives). Нельзя обещать обнаружение всех угроз.

## Валидация и устойчивость

- Проверка timestamp в CSV не нормализует значение обратно в ISO-формат. Некоторые неканонические даты могут пройти strptime, но вызвать проблемы в последующем анализе.
- IP проверяется на непустоту, но не на соответствие IPv4/IPv6.
- NOT NULL не запрещает пустые строки и не валидирует семантику полей.
- В таблице events нет дедупликации, поэтому повторный импорт создаёт дополнительные записи.
- SQLite-ошибки не во всех UI-методах перехватываются: часть методов обрабатывает только ValueError и OSError.
- RulesDialog.save не содержит собственной обработки ошибок сохранения.
- UPDATE не проверяет число реально изменённых строк.
- Экспорт CSV не нейтрализует значения, которые могут интерпретироваться как формулы в табличном редакторе.
- Нет явного файла requirements.txt в проверенной версии. Для запуска требуется установленный PyQt6; остальные используемые модули входят в стандартную библиотеку Python.

## Производительность

- Анализ загружает всю историю в память и сортирует группы.
- UI показывает ограниченную выборку последних 1000 событий; поиск выполняется внутри неё.
- QTableWidget заполняется по ячейкам, а анализ синхронно работает в GUI-потоке.
- С ростом истории возможны временные задержки интерфейса. Нет подтверждённых измерений производительности.

## Удалённый мёртвый код

В процессе подготовки проекта к защите удалены:
- ui/pages/rules_page.py — старая неиспользуемая страница, несовместимая с текущим Repository;
- assets/style.qss — неиспользуемая таблица стилей.

Рабочая настройка правила остаётся в ui/rules_dialog.py и соответствующем XML-макете. Пустые __init__.py оставлены: они обозначают обычные Python-пакеты. Исходники рабочего интерфейса, БД и детекторов при очистке не менялись.
