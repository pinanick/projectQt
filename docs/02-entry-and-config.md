# 2. Построчный разбор: `main.py` и `config.py`

Нумерация относится к текущим файлам ветки `main`. Пустые строки разделяют логические блоки и не выполняют инструкций.

## 2.1. `main.py` — запуск приложения

| Строки | Что происходит | Зачем это нужно |
|---|---|---|
| 1 | Строка документации модуля (module docstring). | Кратко описывает назначение файла и команду запуска. |
| 2 | `import sys`. | Нужен для передачи аргументов командной строки Qt и завершения процесса через `sys.exit`. |
| 4 | Импорт `QApplication`. | Этот объект управляет приложением Qt и его циклом событий. |
| 6 | Импорт `generate_events`. | Используется для первоначального заполнения пустой базы. |
| 7 | Импорт `DatabaseManager`. | Создаёт и закрывает соединение SQLite. |
| 8 | Импорт `Repository`. | Даёт остальному приложению единый интерфейс к данным. |
| 9 | Импорт `MainWindow`. | Главное окно приложения. |
| 12 | Объявляется функция `main`. | Отделяет запуск программы от определения модулей и позволяет вызвать запуск явно. |
| 14 | Создаётся `QApplication(sys.argv)`. | Инициализирует Qt. `sys.argv` передаёт Qt аргументы запуска, например параметры платформы. |
| 15 | Задаётся имя приложения `CyberLab`. | Имя используется Qt как метаданные приложения. |
| 18 | Создаётся `DatabaseManager`. | Открывает файл БД, включает внешние ключи и создаёт необходимые таблицы. |
| 19 | Создаётся `Repository(db)`. | Repository использует соединение, созданное DatabaseManager. |
| 22 | Проверяется `total` из `get_event_counts()`. | Начальная генерация запускается только при пустой таблице событий. |
| 23 | Генерируется 40 фоновых событий плюс встроенная подозрительная последовательность; затем они сохраняются. | При первом запуске интерфейс не пустой, можно сразу демонстрировать функции. |
| 26 | Создаётся `MainWindow(repo)`. | Главное окно получает доступ к данным через Repository. |
| 27 | `window.show()`. | Показывает окно на экране. Без этого окно было бы создано, но не отображено. |
| 28 | Начало блока `try`. | Гарантирует выполнение закрытия БД при штатном выходе из цикла событий и при исключении внутри него. |
| 29 | `app.exec()`. | Запускает цикл событий Qt: обработку кликов, клавиатуры, перерисовки и сигналов. |
| 30 | `finally`. | Блок выполняется после завершения `try`, независимо от того, завершился ли вызов нормально или выбросил исключение. |
| 31 | `db.close()`. | Закрывает соединение SQLite, освобождая ресурс. |
| 34 | Проверка `__name__ == "__main__"`. | Не запускает приложение при импорте `main.py` из другого модуля. |
| 35 | `sys.exit(main())`. | Запускает программу и передаёт код возврата операционной системе. |

### Важная оговорка про `finally`

Этот блок закрывает соединение после завершения `app.exec()`. Он не является обработчиком всех ошибок, которые могли произойти до входа в `try` (например, при создании окна). Для учебной версии это простая схема управления ресурсом; более строгий вариант обернул бы весь жизненный цикл БД в контекстный менеджер или внешний `try/finally`.

### Что могут спросить

**Почему нельзя убрать `app.exec()`?** Окно может появиться и сразу закрыться, потому что не будет работать цикл обработки событий.

**Почему Repository один на все страницы?** Чтобы все части интерфейса работали с одной базой и одним набором методов доступа к данным.

**Почему генерация только при пустой БД?** Чтобы при каждом запуске не добавлять ещё одну копию стартового набора событий.

**Что хранит `sys.argv`?** Список аргументов командной строки; первый элемент обычно имя запускаемого скрипта.

## 2.2. `config.py` — общая конфигурация

| Строки | Что происходит | Зачем это нужно |
|---|---|---|
| 1 | Docstring модуля. | Описывает назначение конфигурации. |
| 2 | Импортируется `Path` из `pathlib`. | Обеспечивает объектную работу с путями вместо ручной склейки строк. |
| 4 | `BASE_DIR = Path(__file__).resolve().parent`. | Получает абсолютный путь к каталогу, в котором находится `config.py`. `__file__` — путь текущего файла; `resolve()` нормализует его; `parent` берёт каталог. |
| 5 | `DB_PATH` строится как `BASE_DIR / "data" / "cyberlab.db"`. | Оператор `/` у Path соединяет части пути. База располагается в каталоге проекта, а не зависит от текущей рабочей директории запуска. |
| 7 | `FAILED_LOGIN_THRESHOLD = 5`. | Стандартный порог первого детектора: пять ошибок. |
| 8 | `FAILED_LOGIN_WINDOW_SECONDS = 60`. | Временное окно первого детектора — 60 секунд. |
| 9 | Комментарий о втором детекторе. | Разделяет параметры двух разных эвристик. |
| 10 | `SUCCESS_AFTER_FAILURES_THRESHOLD = 3`. | Для второго детектора требуется минимум три предыдущие ошибки. |
| 11 | `SUCCESS_AFTER_FAILURES_WINDOW_SECONDS = 120`. | Ошибки должны находиться в пределах 120 секунд до успешного входа. |
| 12 | `MAX_VISIBLE_EVENTS = 1000`. | Ограничивает количество событий, загружаемых в страницу журнала. Это лимит отображаемой выборки, не лимит базы. |
| 14–18 | Словарь `EVENT_LABELS`. | Сопоставляет внутренние коды событий с русскими подписями интерфейса. |
| 20–23 | Словарь `INCIDENT_LABELS`. | Сопоставляет внутренние типы инцидентов с понятными названиями. |

### Почему коды хранятся на английском, а интерфейс на русском?

Короткие стабильные идентификаторы удобно использовать в логике и базе данных. Пользовательские подписи можно менять независимо от алгоритмов. Например, код `login_failed` остаётся прежним, даже если текст в интерфейсе будет изменён на «Неудачная авторизация».

### Важное отличие двух окон

- Первый детектор использует значения из таблицы `rules` через `Repository.get_rule()`.
- Второй детектор использует константы из `config.py`.

Поэтому диалог настройки изменяет только первый детектор. Нельзя утверждать, что пользователь настраивает оба правила через одно окно.
